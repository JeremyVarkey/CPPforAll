# In-browser Run/Submit — architecture plan (B1)

## Spike verdict (B0, measured)
- Wasmer SDK `clang/clang` in-browser: loads in ~2s, compiles+links 2 small TUs in 825ms,
  runs artifacts. **But effective compile throughput is ~25KB/s**: any libc++-heavy input
  (`<iostream>`, `<string>`, `<vector>`) times out — 208s+ for a single TU, and a CI-flattened
  3.2MB single-header still exceeds 120s. Same behavior in the local wasmer CLI ⇒ intrinsic
  to the wasm toolchain, not browser FS. Every drill uses `<iostream>` ⇒ **in-browser clang
  is not viable today.** (Assets + method preserved: `clang/clang` webc unpacks a sysroot;
  native `clang -E` over it produces a faithful flattened header in 0.26s — revisit if wasm
  toolchains get an order-of-magnitude faster.)

## Decision: server judge on Azure Container Apps, swappable protocol
The client speaks a **runner protocol** (run request → step results); tonight's backend is a
container judge; a future wasm backend can replace it without UI changes.

### Why this wins on the brief (robust / fast / secure)
- **Fast:** native clang ≈ 1s per drill compile; round-trip 1.5–3s warm. Cold start (scale
  from zero) ≈ 5–10s, shown as a "warming up" state.
- **Robust:** the exact toolchain the drills were verified with (clang, C++17); manifests
  replay-tested (solution→green, starter→red) in the same image that serves.
- **Secure:** learner code never touches our origin (judge is a separate host); the client
  sends ONLY editable starter files — tests/headers/expected outputs live server-side
  (hidden-tests property, anti-hardcoding); container runs non-root with per-request
  tmpdirs, rlimits, wall-clock kill, output caps, CORS allow-list, per-IP rate limit;
  no COOP/COEP needed on the site (no SharedArrayBuffer).
- **$0-ish:** ACA consumption plan, minReplicas=0 ⇒ idle cost ~zero, on the VS credit.

## API contract (the spec agents build against)
`POST /run`  body ≤ 256KB:
```json
{ "chapter": 9, "mode": "submit", "files": { "starter/desk.cpp": "<full text>" } }
```
- `files` keys MUST match the chapter manifest's `editable` list — anything else → 400.
- `mode`: `"run"` (compile + run, stdout returned) | `"submit"` (full grader steps).

Response 200:
```json
{ "chapter": 9, "overall": "red|green|error",
  "steps": [ { "name": "unit tests", "phase": "compile|run|grade",
               "exit": 0, "verdict": "pass|fail|error",
               "stdout": "≤64KB", "stderr": "≤64KB",
               "detail": "unified diff or check summary, optional" } ],
  "timings": { "queueMs": 0, "compileMs": 0, "runMs": 0 } }
```
Errors: 400 invalid, 413 too large, 429 rate-limited, 503 at capacity. CORS:
`https://cppforall.com` (+ localhost dev). No cookies, no auth, no state.

## Judge container
- Node 22 + clang/lld (or g++) + the repo's `content/drills/` baked in at build.
- Per request: validate → mkdtemp → write pristine chapter files + learner's editable files
  → execute manifest steps with `execFile` (args arrays, never shell) → grade → cleanup.
- Limits: CPU 10s (rlimit), wall 15s kill, AS 512MB, FSIZE 10MB, NPROC 32, stdout/err 64KB
  caps, ≤4 concurrent jobs per instance (in-process queue), non-root user, tmpfs workdir.
- Rate limit: token bucket per IP, 10 runs/min burst 20 → 429.
- `GET /healthz` for probes; `GET /manifest/:chapter` returns the public bits (editable
  files list) for client validation.

## Grader manifests (`judge/manifests/chapter-NN.json`, generated + committed)
Generated by `scripts/build-grader-manifests.mjs` from the verified Makefile inventory:
- common: `clang++ -std=c++17 -Wall -Wextra` (+ per-chapter `-I` flags)
- Style A (ch01): compile starter/main.cpp → run with stdin tests/input.txt → verdict
  `diffExpected` vs tests/expected.txt (normalize trailing ws + final newline).
- Style B (most): compile tests/tests.cpp + starter/<name>.cpp → run → verdict `exitCode`.
- Style B2 (ch 11/14/26): compile tests/tests.cpp with `-Istarter` → run → `exitCode`.
- ch09: two steps (unit tests `exitCode`; cin_driver run with stdin tests/cin_input.txt →
  `grepDiff` lines `^ACCEPTED=` == ["ACCEPTED=7","ACCEPTED=50"]).
- ch28: workdir contains writable `tests/` so `fstream` on tests/tmp_report.txt works.
- `editable`: the starter/* file list (the ONLY client-suppliable paths).
- **Replay gate:** `judge/test-manifests.mjs` runs every manifest against pristine starter
  (must be red) and solution (must be green) — wired into the container build so a bad
  manifest fails the image, never a learner.

## Client (ExerciseRunner island, Phase-B design slot)
- React island, `client:only`, lazy — mounts in the reserved run-slot on exercise pages.
- CodeMirror 6 (`@codemirror/lang-cpp`), dark theme bound to the design tokens; editable
  tabs for `editable` files (pre-filled with starter code), read-only for the rest.
- Buttons per design: coral **Run**, green **Submit**; results strip = per-step pills
  (red/green), expandable console (stdout/stderr, diff detail for ch01).
- States: idle → warming (cold start) → compiling → running → verdict; offline/429/503
  → friendly message + keep copy/download path. localStorage drafts per chapter.
- Judge base URL via `PUBLIC_JUDGE_URL` env (build-time), so preview/prod can differ.

## Azure
- ACR `cppforallacr` (Basic) + ACA env + app `cppforall-judge` in `rg-cppforall`
  (ALWAYS `--subscription "Visual Studio Enterprise Subscription"`), ingress external
  HTTPS, minReplicas 0, maxReplicas 3, 0.5 vCPU / 1Gi.
- Custom domain later (judge.cppforall.com) — default ACA hostname is fine for v1.

## Delegation (Opus builders, per Jeremy's explicit instruction)
1. **judge-server** (Opus): `judge/` — server.mjs, runner.mjs, limits, rate limiting,
   Dockerfile, test-manifests.mjs. Builds against this contract verbatim.
2. **manifests** (Opus): `scripts/build-grader-manifests.mjs` + generated
   `judge/manifests/*.json` for all 28, from the Makefile inventory rules above.
3. **runner-ui** (Opus): `src/islands/ExerciseRunner.tsx` + CodeMirror wiring + styles
   (token-bound), mounted from the exercise page; graceful degradation.
Orchestrator: this plan, the contract, ACA/ACR provisioning, integration, independent
verification (red→green matrix vs native make), final review.
